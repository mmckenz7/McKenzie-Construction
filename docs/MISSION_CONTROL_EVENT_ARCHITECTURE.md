# Mission Control Intelligence: Event Architecture

**Status:** architecture approved; additive proposal and communication foundations plus an owner/admin diagnostic signal API are implemented, with dashboard changes still deferred

**Repository baseline:** integrated `beta/estimating-core` at `829298a`

**Design date:** 2026-08-10

## Executive recommendation

Mission Control should answer **“What needs my attention today?”** from recorded facts and deterministic, versioned rules. It should not infer operational conclusions directly from arbitrary mutable rows, free-form notes, or an AI model.

The recommended foundation has four distinct layers:

1. Existing domain tables remain the operational source of truth.
2. A new append-only `business_events` ledger records selected, meaningful business facts at the workflow boundary.
3. Rebuildable projections aggregate those events, and a deterministic rule engine creates current `mission_control_signals` with explicit evidence.
4. A later AI layer may summarize and rank already-created signals, but may not manufacture facts, change rule outcomes, or take action without an authorized workflow.

Do **not** automatically turn every database mutation into a business event. Broad row-change history belongs in a separate technical audit log. Events such as `proposal.issued`, `customer.email_replied`, `inspection.failed`, and `payment.received` are business facts. Changes such as “JSON metadata changed,” “row updated,” or “retry counter incremented” are not Mission Control facts by themselves.

The smallest useful V0 is a narrow, owner/admin-only signal feed built from four well-supported rules: unanswered customer replies, proposal follow-up opportunities, proposals nearing expiry, and expired proposals requiring pricing review. The existing `/all-work` dashboard should not be redesigned during the foundation work.

The additive foundation and first two producer slices now exist in:

- `supabase/migrations/20260810072000_mission_control_event_foundation.sql`;
- `supabase/migrations/20260810081000_mission_control_proposal_events.sql`;

- `supabase/migrations/20260810085000_mission_control_v0_evaluator.sql`;
- `src/lib/mission-control/event-contracts.ts`;
- `src/lib/mission-control/record-business-event.ts`;
- `tests/mission-control-*.test.mjs`;
- `supabase/tests/mission_control_*.sql`.

These slices create the append-only ledger, deterministic signal storage, service-role-only emitter, narrow V0 contract registry, proposal issue generations, append-only proposal access observations, transactional proposal and email facts, scheduled proposal expiry, and four deterministic signal rules: proposal follow-up, proposal expiry warning, expired-proposal pricing review, and unanswered customer email. A service-role-only V0 evaluator runs all four rules atomically at one supplied evaluation time; connecting it to a scheduler remains a deployment decision. Events and signals carry bounded factual evidence and do not store proposal tokens, message bodies, email addresses, or unrestricted provider payloads. The work does not change `/all-work`, invoke AI, deploy, or modify Production.

The hidden `GET /api/mission-control/signals` verification boundary exposes only those four V0 rules to active owners and administrators. It resolves and applies the singleton company anchor even though it reads with the service role, excludes still-snoozed signals, uses deterministic severity/due-time ordering, caps the response at 100 records, disables caching, and performs no evaluation or mutation. It is an internal contract for verifying rule evidence, not a dashboard redesign.

The proposal access record deliberately says **access observed**, not verified customer view, because server requests can be generated by link scanners. Follow-up requires at least two current-generation browser-confirmed observations after 72 calendar hours by default, while its rule output explicitly records `verified_human_view: false`. The communication rule requires an identity-matched inbound message and its receipt event; unmatched mail is suppressed rather than guessed. All integration tests execute inside rollback-only local transactions.

## 1. Repository findings

### Current architecture and build state

- The application is Next.js 16 with Supabase/Postgres.
- The requested branch builds successfully with `npm run build` as of this design pass.
- Server routes commonly authenticate an employee, then use the Supabase service-role client. This makes route-level authorization and tenant scoping essential because RLS is bypassed by those queries.
- The current schema is explicitly single-company. `company_settings` is treated as a singleton, and business tables do not have `company_id`, `tenant_id`, `workspace_id`, or an equivalent ownership column. Existing change-order reporting functions intentionally reject an unexpected tenant-column layout.
- `/all-work` is already branded “Mission Control,” but it is a live query dashboard over tasks and mutable state. This document does not propose changing its UI yet.

### Existing activity and audit infrastructure

#### `lead_activities`

This is a useful CRM/sales timeline. It records:

- a text `lead_id`;
- free-form `activity_type`;
- constrained channel and direction;
- summary, details, timestamp, external ID, and JSON metadata.

Current producers record meaningful facts including lead submission, lead/consultation status changes, assignment changes, calls and outcomes, consultation changes, follow-ups, estimate workflow activity, sent emails, inbound SMS, estimate acceptance/decline, and estimate expiry.

Important limitations:

- no company/tenant key;
- no actor type or actor ID;
- no general idempotency constraint (`external_id` is only indexed);
- no entity model beyond a legacy text `lead_id`;
- application workflows often update domain state and insert activity in separate calls, so they are not transactionally atomic;
- activity insertion errors are sometimes logged without failing the business operation;
- lead deletion explicitly deletes `lead_activities`, so it is not a durable append-only ledger;
- free-form `activity_type` values have no versioned contract.

#### `project_activity`

This is a richer project timeline. It includes project, actor type, employee/subcontractor references, source table/ID, metadata, and occurrence time. It already covers change orders, payments, installer schedule responses, material reviews/issues, project messages, inspections, and manual notes. Many inspection RPCs create semantically useful records inside the same database transaction as the workflow change.

Important limitations:

- no company/tenant key;
- actor types do not consistently model customer, vendor, integration, and employee identities (a later migration added customer attribution for a specific path, but the baseline remains inconsistent);
- `activity_type` is a large closed check constraint, making extensions migration-heavy;
- the unique `(activity_type, source_table, source_id)` rule conflates event identity with source entity identity;
- some producers generate random `source_id` values rather than linking to the actual source fact;
- some triggers update an existing activity row on conflict, so the table is not strictly append-only;
- the generic project update trigger records nearly any changed project field. That is closer to technical audit history than a curated business-event stream;
- project deletion cascades to activity deletion;
- message activity can be overwritten as translation/delivery fields change.

`project_activity` should remain a user-facing timeline during migration. It should not become the universal Mission Control ledger unchanged.

#### Communications infrastructure

The communications subsystem has several reusable fact sources:

- `communication_outbox` has a real unique `idempotency_key`, delivery attempts, provider IDs, source references, and timestamps.
- `communication_messages` records inbound/outbound email/SMS/voice, provider IDs, message/thread association, status, and sent/received timestamps. Its unique provider/message/direction index supports replay safety.
- `communication_threads` records participants, unread count, assignment, status, and `last_message_at`.
- `communication_provider_events` is an append-like, provider-event ledger with a unique `(provider, event_id)` constraint and occurrence/processing timestamps.
- Microsoft Graph inbox sync captures customer replies; Resend webhooks capture delivery events; Twilio currently records inbound SMS and opt-out facts.

`communication_provider_events` is a **technical integration ledger**, not the business-event ledger. A verified provider event may produce a business event such as `communication.email_delivered` or `communication.email_bounced`, while the raw webhook record remains available for replay and diagnostics.

Current gaps include no company key, incomplete normalized delivery states (for example, “opened” depends on provider support), and no uniform relationship from every message to lead, customer, estimate, contract, or project.

#### Estimating and proposals

Reusable facts include:

- structured estimates and immutable-at-issuance proposal snapshots;
- proposal status, `issued_at`, `expires_at`, first `opened_at`, response, `responded_at`, and `revoked_at`;
- accepted/declined response activity;
- deterministic expiry-to-pricing-review behavior and an idempotent open pricing-review task check;
- estimate cost, price, profit, margin, and material-price snapshots.

Critical gaps:

- proposal issuance and revocation do not consistently emit durable business events;
- only the first proposal open is retained. “Viewed three times” cannot be supported today;
- reissue updates the single proposal row and resets lifecycle timestamps, so issue generations and access history are lost;
- expiry status is advanced lazily when the public token is accessed. `expires_at` is authoritative, but a scheduled detector is required for timely Mission Control signals;
- routine estimate edits are mutable and have no revision/event history. Recording every line-item keystroke would be noise; explicit save/review/issue boundaries are the right producers.

#### Contracts

`estimate_contract_preparations` supports draft, ready, sent-for-signature, signed, and void states plus provider envelope fields. It is a preparation boundary, not a complete contract workflow. There is no complete viewed/declined/expired envelope event history, and current writes do not produce a general business event stream.

#### Projects, scheduling, materials, and inspections

The repository already records many strong operational facts:

- project status, manager, start and target completion dates;
- project tasks and due/completion state;
- schedule readiness and confirmed/calculated start dates;
- material phase status and estimated/confirmed delivery dates;
- installer schedule requests and responses;
- change-order lifecycle, approvals, response history, billing, and payments;
- inspection requested/scheduled/pass/partial-pass/fail state, corrections, and explicit task dependencies.

Gaps relevant to future example outputs:

- there is no complete planned-vs-actual project progress model, so “project is running behind schedule” is not yet a safe general conclusion;
- task status changes and completions do not consistently emit business events;
- material orders/deliveries have current state but not a complete immutable transition history;
- crew assignments, capacity calendars, and forecasted release dates are not modeled well enough to assert that capacity will open early;
- permit facts are partly represented through readiness and inspections, but there is no complete permit lifecycle.

#### Financials

Reusable facts include estimate cost basis, estimated profit/margin, project costs, change-order costs and payments, contract values, change-order invoice dates/due dates, and receivable RPCs. The schema correctly documents that a null invoice due date means overdue state is unknown.

Gaps:

- there is no general invoice/payment ledger outside change-order billing;
- committed cost is not a first-class, consistently modeled amount;
- cost updates do not create an immutable cost history;
- expected/baseline margin and company/project alert thresholds are not modeled;
- current margin can be computed only where revenue and sufficiently complete costs are known. Mission Control must label incomplete cost coverage as unknown, not low margin.

### Gap summary

The existing infrastructure is valuable, but it cannot yet guarantee that a signal is complete, durable, idempotent, tenant-scoped, and backed by immutable evidence. The main missing capabilities are:

1. a cross-domain semantic event contract;
2. strict append-only behavior and stable event identity;
3. consistent actor, company, entity, correlation, source, and schema-version fields;
4. transactional emission at important workflow boundaries;
5. repeatable projections and deterministic signal state;
6. explicit data-quality/unknown handling;
7. multi-tenant ownership before any multi-company deployment;
8. histories for repeated proposal access, issue generations, task changes, material transitions, cost/margin changes, and contract-provider callbacks.

## 2. Business events versus technical audit logs

### Business event inclusion test

Record a business event only when all of the following are true:

- it describes a fact a business user would recognize in past tense;
- it has a stable subject and occurrence time;
- its producer knows enough to state the fact without guessing;
- it can affect a timeline, deterministic rule, compliance record, or downstream workflow;
- retries can be assigned a stable idempotency key.

Good examples:

- `crm.lead_created` version 1
- `crm.lead_stage_changed` version 1
- `estimating.proposal_issued` version 1
- `estimating.proposal_access_observed` version 1
- `communication.customer_email_received` version 1
- `contract.signed` version 1
- `project.material_delivery_delayed` version 1
- `project.inspection_failed` version 1
- `financial.payment_received` version 1

Technical audit examples that should not enter this stream directly:

- an API request completed;
- a webhook retry count changed;
- an `updated_at` column changed;
- a JSON field changed without a defined business meaning;
- a queue row was locked;
- a provider payload was parsed;
- an employee viewed an internal page.

If a full technical audit trail is required, build a separate restricted `technical_audit_log` with its own retention and access policy. Mission Control should never scan it to invent business meaning.

### Event log is not event sourcing

This design does not replace domain tables or rebuild all application state from events. The current lead, estimate, proposal, task, project, inspection, message, and financial tables remain authoritative for current state. `business_events` is the durable record of selected transitions. Projections can be rebuilt from the event ledger, but primary workflows do not depend on replaying the entire application.

## 3. Proposed event model

### `business_events`

Recommended logical schema (names are illustrative until implementation review):

| Field | Purpose |
| --- | --- |
| `id uuid` | Globally unique event ID generated by the authoritative producer. |
| `company_id uuid` | Required tenant/company ownership key. See tenant transition below. |
| `event_name text` | Stable dotted name, including domain and fact, such as `estimating.proposal_issued`. |
| `event_version smallint` | Payload contract version; event meaning is never changed in place. |
| `occurred_at timestamptz` | When the business fact happened, preferably from the authoritative provider/workflow. |
| `recorded_at timestamptz` | When McKenzie OS persisted the event. Never substitute this for a late provider occurrence. |
| `actor_type text` | `employee`, `customer`, `subcontractor`, `vendor`, `system`, or `integration`. |
| `actor_id uuid` | Nullable internal identity when one exists. It is meaningful only with `actor_type`. |
| `actor_auth_user_id uuid` | Nullable authenticated user for traceability where appropriate. |
| `subject_type text` | Primary aggregate type: `lead`, `estimate`, `proposal`, `communication_thread`, `contract`, `project`, `change_order`, `invoice`, etc. |
| `subject_id uuid` | Primary aggregate ID. Avoid foreign keys that would delete evidence with the aggregate. |
| `project_id uuid` | Optional denormalized project scope for common filtering. |
| `lead_id uuid` | Optional denormalized lead scope for common filtering. |
| `customer_id uuid` | Optional denormalized customer scope for common filtering. |
| `source text` | Producer boundary: `app.crm`, `db.estimate_proposal`, `integration.resend`, `integration.microsoft_graph`, `system.scheduler`, `migration.backfill`, etc. |
| `source_event_id text` | Provider/workflow-native identity when available. |
| `idempotency_key text` | Stable retry identity, unique within company and source. |
| `correlation_id uuid` | Groups events caused by one user command, provider delivery, or job run. |
| `causation_event_id uuid` | Optional preceding business event that caused this event. |
| `metadata jsonb` | Small, versioned, allowlisted facts specific to the event. |
| `classification text` | `operational`, `financial_restricted`, or another explicit access class. |

Recommended constraints and behavior:

- unique `(company_id, source, idempotency_key)`;
- check constraints for actor type, classification, nonblank event/source/idempotency fields, and sensible occurrence dates;
- prohibit `UPDATE` and `DELETE` for application roles; corrections are new events such as `financial.cost_entry_corrected.v1` referencing the prior event;
- no cascading foreign keys from the event ledger to mutable/deletable domain rows;
- cap and validate metadata size and keys per event contract;
- store neither public tokens nor provider secrets, raw email bodies, full contracts, raw IP addresses, or unrestricted request headers in metadata;
- use an event-contract registry in code for payload validation, descriptions, sensitivity, and allowed producers. Do not use a giant database check constraint for every event name.

### Naming and versioning

Use `<domain>.<fact>` plus the numeric `event_version` column. Facts are past-tense concepts even when the name is concise. Do not encode UI severity or a current conclusion in the event.

Examples:

- `estimating.proposal_issued`, version 1;
- `estimating.proposal_access_observed`, version 1;
- `communication.email_delivery_confirmed`, version 1;
- `project.change_order_approved`, version 1;
- `financial.margin_recalculated`, version 1.

An event version is immutable. Add version 2 when required meaning or payload changes. Consumers support explicitly declared versions and fail closed on unknown required fields.

### Actor rules

- `employee`: use the internal app/team identity associated with the authenticated command.
- `customer`: use a known customer ID only when identity is actually established. Public-token access alone does not prove which customer person opened a page.
- `subcontractor` and `vendor`: use the relevant party identity when known.
- `system`: scheduled expiry, deterministic recalculation, and rule execution.
- `integration`: a provider originated the fact and no end-user identity is established.

The phrase “customer viewed proposal” is too strong for a server request that might be a mail scanner. Record `proposal_access_observed` and metadata such as access channel and bot-classification result. Product copy may say “proposal link opened” unless the application has stronger browser/person verification.

### Entity relationships

Every event has one primary subject. Optional denormalized lead/customer/project IDs make tenant-safe filtering fast. Additional relationships should use either a small allowlisted metadata object or a normalized `business_event_entities(event_id, company_id, entity_type, entity_id, relationship)` table if cross-entity queries become common.

Do not put arbitrary table names and unvalidated IDs into a generic polymorphic relationship and then treat them as trusted. Entity types must come from a code-owned registry.

### Idempotency

Idempotency is required at emission time, not cleaned up later.

- Provider webhooks: `<provider>:<provider_event_id>`.
- Synced messages: `<provider>:<mailbox>:<provider_message_id>:received`.
- One-time state transition: `<aggregate_id>:<new_state>:<transition_generation>`.
- Explicit user command: a request/command UUID persisted with the domain mutation.
- Scheduled detector: `<rule-or-event>:<subject_id>:<effective_boundary>`.

Repeated facts need distinct keys. Each real proposal access gets its own request/access ID; retries of the same access do not. Reissuing a proposal needs an explicit issue generation/version so it does not collide with the prior issuance.

### Transactional production

The domain write and its business event should commit together whenever McKenzie OS controls both:

- Database RPC workflows should insert the event in the same transaction.
- Multi-step application routes should move high-value state transitions into a transactional RPC or use a transactional outbox pattern.
- External webhooks should first persist the verified raw provider event idempotently, then create the normalized business event in the same database transaction as message/delivery state changes.
- A failed event insert must fail a workflow that promises durable event production. Silent logging is not sufficient for Mission Control facts.

The following matrix distinguishes what can be emitted now from explicit facts and what requires domain work first.

| Domain fact | Authoritative producer | Current support | Recommendation |
| --- | --- | --- | --- |
| Lead created | Lead creation workflow | Strong; activity exists | Emit transactionally after the lead insert. |
| Lead stage changed | Explicit CRM workflow | Strong; old/new status available | Emit only when the business stage changes, with previous/new values. |
| Employee assigned | Assignment workflow | Strong; activity exists | Include prior/new assignee and authenticated employee actor. |
| Customer contact | Message/call workflow | Partial | Emit sent/received/logged facts by channel; a draft is not contact. |
| Consultation scheduled | Confirmation/reschedule workflow | Strong | Emit scheduled/rescheduled/canceled/completed separately. |
| Task created/completed | Task workflow | State exists, event coverage weak | Emit on explicit task create/complete/cancel; avoid events for cosmetic edits. |
| Lead inactivity | Signal engine, not event producer | Derivable only after activity coverage is reliable | Do not emit “inactive” from `updated_at`; create a signal from last qualifying business activity and policy. |
| Estimate created | Estimate create route/RPC | Strong current state | Emit once. |
| Estimate edited | Explicit save/review boundary | Mutable; no revision history | Emit a coarse `estimate_draft_saved` with revision number, changed sections, and content hash—not every line mutation. |
| Estimate issued | Proposal issue RPC | Strong state, missing durable event | Emit in the issuance transaction with proposal generation and expiry. |
| Proposal accessed/viewed | Public proposal endpoint plus browser evidence | First open only | Add append-only access facts. Preserve scanner uncertainty; aggregate counts separately. |
| Proposal accepted/declined | Response RPC | Strong; activity exists | Emit in the response transaction with customer/public actor and response ID. |

| Proposal revoked | Revoke RPC | Strong state, missing event | Emit transactionally with employee actor and generation. |
| Pricing review | Review task and reissue transition | Partial | Emit `pricing_review_requested` and `pricing_review_completed`; task state remains operational action. |
| Estimate reissued | Proposal issue RPC | Current row is overwritten | Add proposal issue generation/revision before claiming reissue history. |
| Email sent | Outbox processor/provider acceptance | Strong | Distinguish queued, provider-accepted/sent, and delivered. “Sent” must have a precise contract. |
| Email delivered/opened/bounced | Verified provider webhook | Delivery/bounce foundation exists; opens provider-dependent | Normalize only provider-supported facts. Absence of an open is not proof of unread. |
| Customer replied | Microsoft Graph sync/inbound webhook | Strong for linked inbound messages | Emit after idempotent message persistence; preserve thread and related entity IDs. |
| SMS sent/received | Twilio workflow | Partial | Use the same normalized message facts when expanded. |
| Call logged | Explicit CRM call outcome | Partial/strong for outbound outcomes | Record only logged calls; never infer a call from clicking a phone link. |
| Contract prepared | Contract preparation workflow | Strong current state | Emit on creation/ready transition. |
| Contract sent/viewed/signed/declined/expired | Signature-provider webhook | Schema partly ready, integration incomplete | Add only when provider callbacks and envelope identities exist. |
| Project activated/completed | Explicit project workflow | Current state exists | Define activation transition; emit status milestones, not all row updates. |
| Schedule changed | Schedule workflow | Current dates/readiness exist | Emit material changes to committed dates with old/new values and reason. |
| Task delayed | Task/schedule workflow | Not explicit today | Require due-date change reason or objective overdue rule; do not infer “delayed” from any edit. |
| Material ordered | Material phase/procurement workflow | Status exists | Emit on transition to ordered with supplier/order reference if known. |
| Delivery delayed | Material phase/provider workflow | Status/date exists, history absent | Emit when confirmed date moves later or status becomes delayed, with prior/new dates. |
| Inspection scheduled/passed/failed | Inspection RPCs | Strong semantic activity | Dual-write/migrate these transactional producers first. |
| Change order created/approved | Change-order workflow/RPC | Strong activity coverage | Emit semantic lifecycle transitions; omit generic “row updated.” |
| Estimate cost basis | Estimate pricing/review boundary | Strong snapshot fields | Emit a versioned cost-basis snapshot/hash when reviewed or issued, not on every calculation. |
| Committed cost | Procurement/subcontract workflow | Not consistently modeled | Model commitments first; do not approximate them from estimates or actuals. |
| Actual cost | Project cost workflow | Current rows exist | Emit recorded/adjusted/voided facts with restricted financial classification. |
| Invoice issued/payment received | Change-order billing | Strong only for change orders | Emit for change-order invoices now; wait for a general invoice ledger for whole-project claims. |
| Invoice overdue | Signal engine | Deterministic only with issued invoice, positive balance, and nonnull due date | A signal, not a recurring event. Resolve when paid/voided/due date changes. |
| Gross profit changed | Recalculation projection | Partial | Calculate only with explicit revenue and cost coverage; store evidence and completeness. |
| Margin threshold crossed | Signal engine | Threshold/baseline missing | Add approved threshold and baseline first; emit/signal crossings only on complete inputs. |

### Migrating existing activities

Do not replace `lead_activities` or `project_activity` in one release.

1. Introduce the new event contract and emitter.
2. Dual-write a very small set of high-value workflows transactionally.
3. Reconcile counts and payloads in staging.
4. Build read projections from `business_events` for Mission Control.
5. Later, optionally make legacy timeline rows projections of business events.

Historical backfill must be conservative. It may create events only from explicit durable facts such as a response row with `submitted_at` or a payment ledger entry. Backfilled events require `source = 'migration.backfill'`, a deterministic idempotency key, original occurrence time, and metadata identifying the source record. Do not create guessed “lead inactive,” “customer viewed,” “project delayed,” or “margin crossed” history.

## 5. Event aggregation and current facts

Mission Control should not scan an unlimited event ledger or JSON payloads on every page load. Build rebuildable projection tables, updated idempotently by event ID.

Suggested projections:

### `entity_activity_state`

One row per company/entity, containing only well-defined aggregates such as:

- last qualifying activity time;
- last inbound customer communication time;
- last outbound employee response time;
- last event ID processed;
- open task count and nearest due time;
- current proposal issue generation, issue/access/response/expiry times, and observed access count;
- last material delivery change;
- last inspection blocking event.

### Financial/project fact projections

Use typed columns rather than opaque JSON for values used by rules:

- revenue basis and timestamp;
- estimate/baseline cost;
- committed cost;
- actual cost;
- cost coverage status (`complete`, `partial`, `unknown`);
- expected and current margin;
- planned and actual milestone dates.

Projections are disposable and rebuildable. They may be corrected or updated; the underlying events may not.

## 6. Deterministic signal engine

### Signal model

`mission_control_signals` is current workflow state, not an immutable event log. Suggested fields:

| Field | Purpose |
| --- | --- |
| `id`, `company_id` | Signal identity and tenant. |
| `rule_key`, `rule_version` | Code-owned deterministic rule contract. |
| `subject_type`, `subject_id` | Item needing attention. |
| `dedupe_key` | Unique signal instance, commonly rule + subject + lifecycle generation. |
| `status` | `open`, `acknowledged`, `snoozed`, `resolved`, or `dismissed`. |
| `severity` | Deterministic configured band, not AI sentiment. |
| `first_detected_at`, `last_evaluated_at`, `resolved_at` | Lifecycle timestamps. |
| `due_at` | Optional factual/action deadline. |
| `assigned_to_id` | Optional owner of the signal, independent of task assignment. |
| `evidence jsonb` | Event IDs and typed fact references/values used by the rule. |
| `rule_output jsonb` | Template variables and computed values, not free-form AI conclusions. |

Create a separate append-only `signal_evaluations` or `signal_occurrences` record only if auditability of every open/resolve transition is required. At minimum, signal open/acknowledge/resolve actions should themselves emit business events.

### Rule execution

- Rules live in reviewed, versioned code or declarative configurations with strict typed schemas.
- The evaluator accepts an explicit `as_of` clock and company time zone.
- Event-driven evaluation handles immediate transitions; a scheduled sweep handles time-based rules, missed jobs, and reconciliation.
- Every rule explicitly defines eligibility, positive conditions, suppressions, dedupe generation, resolution conditions, severity, and evidence.
- Unknown or incomplete required facts produce **no conclusion** plus an observable data-quality metric. Unknown must never silently become false or risky.
- Business-day calculations use the existing company time zone and an approved calendar policy. Holidays require an explicit calendar; do not claim “business days” beyond the implemented calendar.

### Example V0 rules

#### `customer_reply_unanswered.v1`

Open when:

- a linked inbound customer communication exists;
- the thread/lead/customer remains active;
- no outbound employee message in the same thread occurred after that inbound message;
- the configured response interval has elapsed.

Resolve when an outbound employee response is recorded, the thread is closed with an explicit disposition, or an authorized user dismisses it with reason.

Evidence: inbound message ID/event ID, received time, thread ID, last outbound time (or explicit null), and evaluation time.

#### `proposal_follow_up_opportunity.v1`

Open when:

- an issue generation is active and was issued more than the configured interval ago;
- at least one non-suppressed proposal access was observed;
- no accepted/declined response, revocation, or expiry exists for that generation;
- no later qualifying employee follow-up occurred.

The example “viewed at least twice” must wait until repeated accesses are recorded. V0 may safely use “opened at least once,” or the product must first add access events.

#### `proposal_expiring_soon.v1`

Open when an active proposal has a known `expires_at` inside the configured window and has no response. Resolve on response, revocation, reissue, or expiry.

#### `proposal_pricing_review_required.v1`

Open when `expires_at <= as_of`, no response/revocation exists, and the issue generation has not been superseded. Resolve when a reviewed proposal generation is reissued or the estimate is explicitly closed.

### Rules that must wait

- “Lead inactive for seven days” waits for a documented definition of qualifying activity and reliable cross-channel coverage.
- “Project behind schedule” waits for milestone/progress baselines and actual completion evidence.
- “Delivery threatens tomorrow’s work” waits for a reliable dependency between the material phase, committed delivery, and tomorrow’s scheduled task.
- “Margin fell below expected” waits for baseline margin, threshold, committed-cost modeling, and cost completeness.
- “Crew capacity opens earlier” waits for crew allocations and forecasted release dates.

## 7. Signals, notifications, and tasks

These concepts should remain separate:

- **Event:** immutable fact that happened.
- **Signal:** current deterministic reason something may need attention.
- **Task:** assigned work with an operational lifecycle.
- **Notification:** delivery of awareness through in-app, email, push, or SMS.

A signal does not automatically become a task unless a company-configured policy explicitly says so. V0 should offer an idempotent “Create task” action or link to the existing task. Store `source_signal_id`/`source_rule_key` on the task and ensure one active task per signal generation. Completing a task does not necessarily resolve the signal; the rule’s factual resolution condition does. Conversely, resolving a signal should not silently complete unrelated human work.

Notifications reference a signal and record delivery status separately. Re-evaluation must not repeatedly notify for the same open generation. Escalation policies should be deterministic and configurable.

## 8. Company and tenant isolation

The current repository is single-company. That is a material architecture constraint, not a reason to omit tenancy from the new contract.

Recommended sequence:

1. Decide the canonical company entity. In a single-company V0, the existing singleton `company_settings.id` can be used as a temporary required company anchor only if that invariant is enforced and documented.
2. Before supporting multiple companies, introduce a true `companies` table and company membership model.
3. Add and backfill `company_id` on authoritative aggregates and identities before enabling multi-company event ingestion.
4. Derive an event company from the authenticated membership and authoritative subject row inside a trusted database function. Never accept an unchecked company ID from the browser, webhook query string, or event metadata.
5. Enforce RLS with `company_id` and membership/permission checks. Service-role consumers must include explicit company predicates and centralized authorization.
6. Put `company_id` in every event, projection, signal, task link, notification, and idempotency key scope.

Mission Control must remain single-company-only until this ownership chain is complete. A global service-role query over unscoped events is unacceptable in a multi-company deployment.

## 9. Storage, retention, and performance

### Storage

- Start with one Postgres table; do not introduce Kafka or another event platform for V0.
- Keep payloads small and typed. Store references and decision facts, not copies of message bodies, proposal snapshots, documents, or provider payloads.
- Use `timestamptz` and retain the company time zone only for presentation/rule-calendar calculations.
- Add indexes for `(company_id, occurred_at desc, id)`, `(company_id, subject_type, subject_id, occurred_at desc)`, `(company_id, event_name, occurred_at desc)`, denormalized lead/project IDs, and the unique idempotency tuple.
- Use cursor/keyset pagination. Do not use large offsets.
- Avoid a blanket GIN index on metadata. Add narrow expression indexes only for proven query patterns.

At expected V0 scale, native Postgres is sufficient. Consider monthly range partitioning only after measured table/index size, vacuum behavior, or retention operations justify it. Premature partitioning complicates uniqueness and migrations.

### Retention

Business events should be retained longer than ephemeral technical logs, but “append-only” does not mean legally immortal.

- Define a company/legal retention schedule by event class before production rollout.
- A conservative starting policy may retain operational events for the life of the customer/project plus a reviewed period and retain contract/financial evidence according to applicable accounting, tax, warranty, and contract requirements. Legal counsel/accounting should approve exact periods.
- Provider webhook payloads and technical request logs can have much shorter retention than normalized facts.
- Minimize PII in events so data-subject requests can be handled by deleting/redacting the authoritative profile without destroying required business evidence.
- Archive only with verifiable checksums, restore tests, tenant boundaries, and documented query behavior.

### Performance and freshness

- Update lightweight projections asynchronously from committed events, with idempotent checkpoints.
- Run time-based signal sweeps on a predictable cadence (for example, every 15 minutes for communication response rules and daily/near-boundary sweeps for expiry), subject to product requirements.
- Monitor event-to-projection lag and projection-to-signal lag.
- The Mission Control read path queries open signals and typed projections, not raw events joined to every domain table.
- Reconciliation jobs compare current authoritative state with expected projection state and report discrepancies; they do not silently invent historical events.

## 10. Security and privacy

- Restrict the initial Mission Control feed to owner/admin or an explicit new permission. Financial signals additionally require `view_costs`/`view_profit`-equivalent access.
- Enforce classification in the query layer so a user allowed to see a project blocker does not automatically see its margin or raw cost evidence.
- Public-token and provider endpoints call narrow, security-reviewed emitters; they never receive direct insert access to the ledger.
- Verify webhook signatures before persisting normalized facts.
- Do not store secrets, authorization headers, signature tokens, public proposal/approval tokens, raw message bodies, attachments, full documents, or payment credentials in event metadata.
- Avoid raw IP and user-agent retention. If fraud/replay controls need them, store a scoped salted hash or a short-lived restricted technical record, not a general business-event payload.
- Treat free-form notes as untrusted and potentially sensitive. Deterministic rules must not parse them to establish facts.
- Escape all human-provided text in presentation and never treat event metadata as executable instructions for an AI system.
- Log reads/exports of restricted financial/event data through a separate audit mechanism.

The current use of service-role clients means tests must verify route authorization before any Mission Control query. RLS is defense in depth, not a substitute for route permission checks—and a service-role query bypasses it.

## 11. AI layer later

AI is a presentation and prioritization layer over deterministic signal objects, not a fact detector in V0.

Allowed later uses:

- summarize open signals into a concise daily brief;
- group related signals by customer/project;
- explain why a signal exists using its structured evidence;
- suggest a draft follow-up or task description;
- rank signals using a bounded policy that preserves deterministic severity and deadlines.

Required guardrails:

- supply only authorized, tenant-scoped signals and minimal evidence;
- require every factual statement to reference signal/event IDs internally;
- label missing or stale data;
- do not allow the model to create new operational statuses, mark work complete, send messages, change money, or mutate schedules without a separately authorized command;
- never let the model override deterministic eligibility/resolution;
- store model, prompt/template version, input signal IDs, output, and user action for explainability, with an appropriate shorter retention policy;
- provide a non-AI rendering of the same signals at all times.

An AI summary may say, “Two proposals need follow-up,” because two deterministic open signals exist. It may not decide that a proposal needs follow-up by reading a note and guessing intent.

## 12. Testing strategy

### Event contract tests

- valid/invalid payloads per event name and version;
- required company, actor, subject, timestamp, source, and idempotency fields;
- metadata size, sensitivity, and allowlist enforcement;
- update/delete rejection and correction-event behavior;
- unique replay behavior for application commands and provider webhooks;
- late and out-of-order provider events preserve `occurred_at` and `recorded_at` semantics.

### Workflow integration tests

- domain mutation and event commit or roll back together;
- authenticated employee/customer/system actor attribution;
- proposal issue/access/response/revoke/expire/reissue generations;
- communication sent/delivered/bounced/replied transitions with webhook replay;
- task creation/completion and signal-linked task dedupe;
- inspection/change-order/payment events match existing workflow facts;
- failed event emission cannot silently leave a supposedly event-complete workflow committed.

### Projection tests

- replay from an empty projection yields the same result;
- duplicate events do not double-count;
- out-of-order events produce the correct typed aggregate;
- checkpoint restart is safe;
- event/projection company IDs cannot cross;
- proposal access counts exclude only explicitly defined suppressions and preserve raw observed counts.

### Rule tests

- table-driven fixtures for every positive condition, suppression, resolution, and unknown-data case;
- frozen clock and company time zone;
- DST boundaries, date-only due dates, and approved business-day policy;
- rule-version changes create predictable dedupe/resolution behavior;
- missing due date never becomes overdue;
- partial cost coverage never becomes a margin alert;
- an inbound reply followed by an outbound response does not remain unanswered;
- scanner-uncertain proposal access is not described as a verified person view.

### Authorization tests

- owner/admin visibility;
- sales/operations scope;
- financial classification permissions;
- service-role routes reject unauthenticated/unauthorized users before querying;
- RLS and explicit company filters prevent cross-company reads/writes;
- exports and AI summaries contain only permitted fields.

### Migration and reconciliation tests

- backfill is repeatable and idempotent;
- only explicit source facts are migrated;
- original occurrence timestamps and provenance are preserved;
- staging reconciliation compares legacy activity, domain state, and new events without changing production;
- legacy timelines continue to work throughout dual-write migration.

## 13. Smallest useful V0

V0 should prove trustworthy evidence and deterministic signal lifecycle without changing the dashboard or production workflows broadly.

### Scope

1. Establish the company-anchor decision and owner/admin authorization boundary.
2. Add `business_events` plus strict emitter/contract code, immutability, idempotency, and indexes.
3. Add proposal issue-generation/access history rather than overwriting all useful history.
4. Dual-write only these facts:
   - proposal issued/access observed/accepted/declined/expired/revoked/reissued;
   - customer email received;
   - employee email sent/reply sent;
   - provider delivered/bounced where verified.
5. Add a minimal communication/proposal activity projection.
6. Add `mission_control_signals` and the four rules described above (unanswered reply, follow-up opportunity, expiring soon, pricing review required).
7. Expose a read-only internal API or hidden diagnostic page for rule/evidence verification. Do not redesign `/all-work` yet. **Implemented as the owner/admin-only `GET /api/mission-control/signals` endpoint.**
8. Run staging dual-write reconciliation before any production enablement.

### Explicitly out of V0

- AI summaries;
- general project-delay, capacity, permit, material-threat, and margin conclusions;
- automatic task creation or outbound notifications;
- replacing legacy activity timelines;
- a generic mutation-to-event database trigger;
- multi-company enablement without company IDs on authoritative aggregates;
- production backfill before staging reconciliation and retention/security review.

### V0 acceptance criteria

- Every displayed signal has a rule/version, exact evidence, evaluation time, and resolution condition.
- Replaying the same app command or provider webhook creates no duplicate event or signal.
- A user can see why the signal exists without AI.
- Unknown/missing required facts suppress the conclusion and produce diagnostics.
- Domain write/event atomicity is demonstrated for V0 producers.
- Owner/admin and financial permission tests pass.
- The existing application build and workflows remain unchanged outside the narrow event dual-write boundaries.

## 14. Recommended implementation order after approval

1. Resolve the canonical company/tenant anchor and permission model.
2. Write event contracts and database invariants before adding producers.
3. Model proposal issue generations and repeated access facts.
4. Add transactional emitters to proposal and communication workflows.
5. Build replayable projections and reconciliation tooling.
6. Implement deterministic signals with frozen-clock tests.
7. Validate through a read-only staging diagnostic surface.
8. Only then design the owner-facing Mission Control experience.

This sequence creates a reliable factual substrate first. It avoids binding the future dashboard—and any future AI—to incomplete mutable state or accidental technical logs.
